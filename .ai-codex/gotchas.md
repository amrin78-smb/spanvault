# SpanVault gotchas — read before touching related code

Dense list of non-obvious behaviours. Full detail lives in `CLAUDE.md` (search
sections by name below) and inline code comments — this is a pointer list, not
a replacement.

## Architecture / auth
- **All free-text going into `wireless_clients` must pass through `textOrNull()`** (collector/wirelessCollector.js). PostgreSQL cannot store U+0000 in text AT ALL - it rejects the WHOLE statement with `invalid byte sequence for encoding "UTF8": 0x00`, so one NUL-padded field from Aruba Central silently dropped that entire client from the fleet view (386+ times, recurring every poll; fixed 1.86.8). Stripping is lossless by definition. The same exposure exists for any other vendor payload written to text columns.
- ⛔ **`monitored_devices.netvault_device_id` is TEXT, not INTEGER — and every NetVault id must be compared as `d.id::text`.** NetVault ships in TWO variants: its own schema.sql creates `devices.id` as SERIAL, but UUID-variant installs exist (netvault/schema.sql has an explicit "never touches a true UUID-variant DB" guard). An INTEGER column worked only against SERIAL and broke sync AND import outright against UUID — `invalid input syntax for type integer: "05e34a6b…"` on the FIRST device of every 30-min sync, aborting the whole cycle, with 0 devices ever linked out of 2,357. Three call sites had to change (collector sync UPDATE, import-list Set compare, import `ANY($1::int[])` → `::text[]`). Don't "tidy" the ::text casts away or retype the column back (fixed 1.86.7).
- No local login page. Auth is 100% via the NocVault hub SSO redirect -> `/sso` -> this app's OWN `POST /api/sso` (Express, NOT a Next.js route) -> hub `sso-verify` called server-to-server (a direct browser fetch is CORS-blocked; bit us in 1.71.3/1.71.4).
- `frontend/src/app/api/**` routes other than the NextAuth catch-all are DEAD CODE — `middleware.ts` rewrites every non-`/api/auth/*` request straight to Express BEFORE Next.js routing sees it. A `frontend/src/app/api/sso/route.ts` was added in 1.71.3 (copying DDIVault's pattern), built clean, and never ran at runtime; fixed in 1.71.4 by moving the logic into `api/server.js`. DDIVault's equivalent pattern (next.config.js rewrite allowlist) is NOT transferable here — 4 different `/api/*` architectures exist across the NocVault suite apps.
- Adding a new intentionally-public route needs THREE independent gates cleared, each in a different file, each only surfacing once the previous is fixed (took 3 broken releases in a row for `/api/sso`): (1) `middleware.ts`'s `PUBLIC_API` regex, (2) `api/server.js`'s `WRITE_GATE_EXEMPT` array (only matters for non-GET), (3) `api/server.js`'s `enforceLicense` — TWO separate checks (`isAck`/`isSso` write-block exemption AND the `exemptPaths` disabled-state array).
- `getServerUrl(req)` (api/server.js, used for remote-agent install/dial-back URLs) and `resolveOrigin(req,...)` (used for browser-facing links/hub proxying) have DELIBERATELY OPPOSITE priority: `getServerUrl` checks `SV_PUBLIC_URL` env var FIRST, falling back to the request's Host header; `resolveOrigin` derives from the request Host FIRST, env var only as last-resort. Do not "fix" one to match the other — an installed remote agent must keep dialing the address it was configured with even if an admin later browses via a different hostname; a browser link should always follow the current request's hostname.
- `middleware.ts`'s per-user app-access gate (`appAllowed`) must run on BOTH the page-render branch AND the `/api/*` proxy branch — a gate on only one leaves a denied user's still-valid session able to pull data straight from the API. Release 1.71.1's notes claimed this was done; the commit never touched `middleware.ts`; the real fix didn't land until 1.71.7. Lesson: when a release note claims an enforcement fix, `git show --stat` the commit and re-read the live file — don't trust the notes.
- `/api/internal/*` (currently just `POST /api/internal/agents/push-config`) is blocked outright by `middleware.ts` (never proxied) AND gated to loopback-only inside Express (`requireLoopback`) — belt-and-suspenders because Express alone can't distinguish "the frontend proxy called on behalf of a browser" from "the collector called directly" — both arrive from 127.0.0.1.

## RBAC / site-scoping
- Site-scoping was found MISSING on a batch of similar routes even though a sibling route added in the same commit had it right: `GET /api/service-checks/:id` and `/:id/results` shipped with zero `getSiteFilter` check while `/api/reports/service-detail` in the same diff had it correctly. All three are now fixed. Rule when reviewing a new batch of routes for one resource: check EACH one individually, don't spot-check one and assume the rest match.
- `GET /api/wireless/aps/:id` was missing `getSiteFilter` scoping until the 2026-07-22 bug sweep, even though the sibling list endpoint (`/api/wireless/aps`) and `/api/wireless/aps/:id/clients` both already had it. Made more reachable that day by an Alerts-page deep link giving every role (including site_admin) a prominent UI path straight into this route by AP id.
- Also fixed in the same class of bug (2026-07 security fix): `GET /api/wireless/clients/:mac` and `/:mac/history` had zero site-scoping, letting a site_admin read another site's wireless client bandwidth/RSSI/connection-event history by MAC or AP id.
- `getSiteFilter(req)` reads `x-user-sites`/`x-user-role` headers set by the frontend proxy from the verified session — a `site_admin` is scoped, admin/viewer/missing headers get `null` (no filter). Enforced server-side in Express, not just client-side, so a site_admin can't bypass it by calling the API directly.

## Distributed polling agents (Phase 3 hub-JWT + duplicate-row fix)
- `api/ws-server.js`'s agent WS auth is accept-both: a hub-signed JWT (`Authorization: Bearer <jwt>`, verified locally against `NEXTAUTH_SECRET` via `agent-identity.js`, cross-checked against NetVault's `agents.revoked_at` for live revocation) is tried first; on any failure it falls through to the legacy `api_key` DB lookup completely unchanged. `agents.hub_agent_id` (TEXT UNIQUE, nullable) marks a hub-enrolled row; `agents.api_key` is nullable since Phase 3 (JWT-provisioned rows have none). See CLAUDE.md's "Phase 3/4a — hub-JWT agents" section for the full model.
- A JWT-authenticated connection with no matching `hub_agent_id` row auto-provisions one at connect time (`INSERT ... ON CONFLICT (hub_agent_id) DO UPDATE`) — this is UNAVOIDABLY blind at that point, because the JWT carries no hostname (the hub mints it before it has ever seen the agent) and config must be pushed immediately on connect. Without the fix below, migrating an EXISTING api_key agent to hub-JWT mode (config swap + restart) stranded its old row (history/site-assignment orphaned) and auto-provisioned a second, empty one — exactly the risk `netvault/docs/nocvault-agents-phase3-plan.md`'s own "duplicate row" section warned about and that shipped unfixed initially.
- Fix, two-part (matches the plan doc's own suggested mitigation): (1) `tryLinkAgentByHostname()` in ws-server.js runs on the agent's FIRST `heartbeat` message (sent immediately on WS open, before the 30s interval — the earliest point a hostname is known) and, on an UNAMBIGUOUS hostname match against an existing legacy row, merges them via `mergeAgentRows()` (reassigns every agents.id-FK'd row, stamps `hub_agent_id` onto the legacy row, deletes the provisional duplicate) and re-keys the live socket (`connectedAgents` + the connection closure's `agent`/`agentKey` `let` bindings) onto the merged row for the rest of that connection. (2) `POST /api/agents/:id/link-legacy` (admin-only) is the manual fallback for when the hostname match is ambiguous (duplicate hostnames) or not yet available — an admin picks the legacy row to merge into from the agent detail page's "Link to existing agent" picker (shown only for a hub-enrolled row). Both share `mergeAgentRows()` — one merge routine, two ways to pick the pair.
- ⛔ **The `::text` casts on `$3` in the `heartbeat` UPDATE (`handleAgentMessage`) are REQUIRED — never "tidy" them away.** `$3` is used BOTH as a plain assignment (`hostname=$3`) and inside a bare `$3 IS NOT NULL` NullTest in the `name=CASE` arm added by the hostname-adoption fix. PostgreSQL cannot infer a type for a parameter in that combination and rejects the statement at PARSE time — `could not determine data type of parameter $3` — so EVERY heartbeat threw into the message handler's catch. Symptom is deeply misleading: the agent stays connected and its ping/snmp results keep arriving normally (they're a different `case` in the same switch), but `last_seen_at` never advances, so the 90s monitor flips the agent to `offline` and its devices to `agent_offline` ~92s after connect, permanently. `version`/`hostname` also stay NULL, so a hub-enrolled agent shows as its raw `agt_…` id with a blank version. Hit **16,665 times** in production before it was found (fixed 1.86.1), and it broke BOTH legacy api_key and hub-JWT agents. Verify any change to this statement against a live DB — a readonly role returning `permission denied` (rather than the type error) proves it at least PLANS.
- Known limitation, accepted: hostname matching has no stronger signal to fall back on (no per-agent MAC/serial collected today) — two genuinely different hosts sharing a hostname, or a legacy row with a stale/wrong hostname, can auto-merge into the wrong row. The manual-link route exists for exactly the ambiguous case (>=2 candidates skip the auto-merge), but a false-positive EXACT single match isn't detectable from this signal alone.
- The restart/logs local-WS-push routes (`POST /api/agents/:id/restart`, `/logs/refresh`) now refuse with 409 for a hub-enrolled agent (`hub_agent_id` set) — hub-enrolled agents' restart/logs run through the hub's own poll-carried `agent_commands` queue instead; sending both would be two live, uncoordinated ways to trigger the same action with no way to tell which one actually ran. This refusal is LOCAL-agent-safe: `hub_agent_id IS NULL` agents (not hub-enrolled — the hub has no session with them at all) are completely unaffected, this is their ONLY restart/logs path. The frontend mirrors this: `GET /api/agents` now includes `hub_agent_id` in the list query (previously detail-only), and both agent pages disable/hide the local restart/logs UI + show a note pointing at the hub's Agents page for a hub-enrolled row; list-page bulk restart pre-filters hub-enrolled ids out of the batch rather than relying solely on the 409.

- ⛔ **Routes registered in the early `/api/internal/*` block (before `enforceLicense`/the RBAC write gate) must NOT use `wrap()`.** `wrap` is a `const` declared much further down `api/server.js`, so referencing it during module evaluation up there throws `Cannot access 'wrap' before initialization` (TDZ) and the API **crash-loops on boot**. `node --check` does NOT catch it — it is a runtime error, not syntax — so it passes every static check and only fails on the server. That is exactly why `/api/internal/agents/disconnect` uses a plain handler with its own `.catch`; do the same for any new route in that block. Shipped once (1.86.3) and caught by the updater's automatic rollback. **Smoke-test with `node -e "require('./api/server.js')"` before deploying an api/server.js change** — it evaluates the module and surfaces this class of error immediately.

- **Agent results for a deleted device are skipped, not inserted.** `monitored_devices` rows can vanish (deleted, or reassigned off this agent) while the agent still holds results for them — buffered offline, or simply in flight before the next config push. Both `ping_result` (INSERT…SELECT…WHERE EXISTS) and `handleSnmpBatch` (one existence probe before the sample loop) now drop those rows silently. Before this the device_id FK rejected each one, the exception unwound the whole message handler (so the `monitored_devices` status update was skipped too), and it logged 315 failures on the production box. Don't "restore" the plain INSERT.
- **`app.param('id', …)` rejects any non-numeric `:id` with a 400 before routing.** All 67 `/:id` routes treat the param as an integer (64 via a bare `parseInt`, the rest via `safeInt`), and the bare ones never checked the result — so `/api/devices/undefined` reached Postgres as `NaN` and 500'd (90 occurrences). This is a whole-class guard; if you ever add a `/:id` route whose id is NOT numeric, give the param a different name rather than loosening this.

## Wireless collector / RF specifics
- `testController(pool, controller)` is commented "dry run — no DB writes" and IS true for SNMP controllers, but is DELIBERATELY FALSE for API controllers with a rotating credential (currently just `aruba_central`): it forwards `pool` into `pollApiController` so a refreshed OAuth token gets persisted. Aruba Central's `refresh_token` ROTATES on every use — if the newly-issued token from a "Test Connection" click isn't saved, the only refresh_token left in the DB is invalidated, permanently bricking the integration (fixable only by a human re-authorizing in the Central UI). Don't drop the `pool` argument to make the "dry run" comment literally true.
- Aruba Central's per-AP RF data (channel/util/tx-power/noise-floor) comes from a SEPARATE, slower poll cycle (`pollRf`, default 900s/15min, `SV_ARUBA_RF_POLL_INTERVAL_SECONDS`) — NOT the main 5-min AP poll, which deliberately never reports RF for aruba_central (rate-limit budget: ~2300 calls/day on the main cycle vs ~770/day on its own, staying under Central's ~5000/day cap). Never fold this back into the main poll.
- Corollary: `upsertAp()`'s RF columns (`radio_2g/5g_channel`, `_util_pct`, `tx_power_2g/5g`, `noise_floor_2g/5g`) are written via `COALESCE($n, existing_column)`, never a plain overwrite — because the main poll always contributes `null` for aruba_central's RF fields. Without the COALESCE, the next main poll (5 min later) would silently wipe out what the 15-min `pollRf` cycle just wrote. Never "clean up" these into plain assignments.
- `pollRf` never refreshes the OAuth token itself — it reuses whatever the main `poll()` last persisted and skips the cycle if the token is missing/expired. A second independent refresher here would risk racing two refreshes inside Central's ~15-min refresh window.
- Wireless RF alerting (`evaluateWirelessAlerts()` in collector.js) is WINDOWED/SUSTAINED, not single-poll: `wireless_high_util` compares a rolling-window average, not one poll's reading, because a genuinely busy AP's utilization swings poll-to-poll (9-73% observed) and rarely lands above a single-poll cliff. 7 checks total, each independently configured via `settingInt()`/`setting()` (14 `app_settings` keys, code-default-only, NO Settings-page UI): `wireless_high_util` (warn/crit two-tier), `wireless_high_retry`, `wireless_client_imbalance`, `wireless_high_interference`, `wireless_degraded_noise_floor`, `wireless_roam_storm`, `wireless_weak_clients`.
- `wireless_client_imbalance` only evaluates a band the AP actually has a radio for (channel not null) — never flag a 0-client band the AP doesn't physically have.
- `wireless_degraded_noise_floor`'s comparison is inverted and easy to get backwards: noise floor is negative dBm, "degraded" means the rolling average is `>=` the threshold (LESS negative = worse; -80dBm is worse than -95dBm).
- Escalating a two-tier alert (e.g. `wireless_high_util` warn->crit) needs resolve-then-re-raise, NOT a second `raiseWirelessAlert` call — the `alerts` table's partial unique index (one ACTIVE row per ap+type) means `ON CONFLICT DO NOTHING` silently no-ops a second raise at a higher severity while the warn-tier row is still active, permanently capping the alert at whichever severity fired first.
- `computeCongestionScore()` (collector/wirelessScore.js, pure function, no DB access) blends util(35%)/retry(25%)/interference(15%)/imbalance(15%)/weak-client-ratio(10%) into a 0-100 score + low/medium/high level. Fixed in the 2026-07-22 bug sweep: the ORIGINAL 70/40 level cutoffs meant util saturated at 100% (worth only 35 of its own weight) could never alone escape "low" — directly contradicting the file's own "util dominates" comment. Cutoffs are now 60/35, derived by hand against what the weighted components can actually produce (util alone maxed=35 -> at least medium; util+retry both maxed=60 -> high). Re-derive by hand again if the weights ever change.
- Congestion score is DISPLAY-ONLY, computed live at read time in `GET /api/wireless/aps` and `/aps/:id` — nothing in the collector persists it, no new column on `wireless_aps`. The API's rolling window is a FIXED 15-minute `INTERVAL`, not a read of the `wireless_util_window_minutes` setting (deliberate simplification) — if that setting is ever changed from its default, the score's window silently drifts out of sync with the alerts' window. `congestion_score`/`congestion_level` are always `null` together for a non-`online` AP, never a misleading `0`/`'low'`.
- `wireless_clients` rows are HARD-DELETED after 15 min of inactivity and get a brand-new `id` on reconnect — never FK a history/alert table to `wireless_clients.id`; key off `(mac_address, controller_id)` instead (this is why `wireless_client_history` and the `wireless_client_bandwidth_high` alert both use mac+controller, not a client row id).
- Client-poll counters (`prevClientCounters`) live in a SEPARATE Map from AP-poll counters, pruned on the CLIENT_POLL_INTERVAL (10min), not the AP one (5min) — reusing the AP map would evict a client's counter baseline moments before its own next poll needed it.
- `wrapAwareDelta`/`counterDeltaBps` apply a sanity cap (`MAX_SANE_BPS = 2e9`) on EVERY delta branch, not just the Counter32-wrap-recovery branch — a collector-restart timing artifact on the "normal" branch alone previously produced one-off multi-hundred-Gbps readings before self-correcting on the next poll.
- Client sustained-bandwidth alerting requires TWO consecutive over-threshold polls (in-memory debounce, `clientBandwidthBreaches` Map) before raising — one large file transfer on a single poll must not alert; a collector restart just resets the counter (delays, never falsely raises).
- Rogue/unmanaged AP detection, HA peer roster (`ha_peers`), and chassis-temp columns are all live-verified against real Aruba hardware per inline comments — don't assume a field name is speculative without checking the comment first.

## Reports / scheduling
- `GET /api/reports/pdf/:template` only accepts templates with a real pdfkit renderer in `api/reportsPdf.js` (`hasPdfRenderer`) — everything else 404s; DB/stack errors are never leaked to the client.
- Two independent PDF/report code paths exist by design: `api/reportsPdf.js` (pdfkit, server-side, used for on-demand PDF download AND scheduled emails via `api/reportScheduler.js`) vs the `frontend/src/components/reports/*Report.tsx` renderers (browser `window.print()` path for the interactive Reports page). This is a deliberate two-path split, not duplication to consolidate (see the analogous documented decision for SpanVault's own reporting hybrid).
- `api/reportScheduler.js`'s `runAndEmailReport` never uses nodemailer's `raw` option — load-bearing for the deferred nodemailer v6->v9 security-debt decision in CLAUDE.md (the v6 CVE requires the `raw` option to be reachable).

## Testing
- `tests/` is OFFLINE PARSER UNIT TESTS ONLY — no framework (plain Node scripts, `spawnSync` per suite), no network, no DB. Run via `node tests/run-parser-tests.js` or `npm run test:parsers`; exits non-zero on any failure (CI-gateable). Covers `collector/wireless/*` vendor SNMP parsers (Aruba, Cisco, Ruckus, Mikrotik, HPE, Fortinet, Grandstream) against synthetic MIB-shaped walk data. Run this after ANY change to `collector/wireless/*` or `collector/snmp-session.js`.
- Playwright is NOT a project dependency (not in package.json, no config file anywhere in the repo) despite commit messages referencing "confirmed live via a Playwright screenshot" — those refer to AD HOC manual UI verification during development sessions (e.g. an MCP browser tool), not a checked-in test suite. Don't go looking for a `playwright.config.ts` or `e2e/` directory; there isn't one.

## Updater / deployment resilience
- `installer/Update-SpanVault.ps1` has DDIVault/LogVault-style self-healing (added alongside NetVault's equivalent). Before touching anything, it snapshots (via `Rename-Item` — metadata-only, cheap regardless of directory size) the pre-update git commit plus THREE directories: root `node_modules` (API/Collector are plain JS, no build step — a broken `npm install` can break them directly), `frontend\.next`, and `frontend\node_modules` — SpanVault has no `output: 'standalone'` build, so there's no single self-contained bundle to snapshot like NetVault's. Every failure path (git pull, either npm install, the frontend build, a real schema-migration SQL error, service start, or the now-mandatory post-start `/api/health` poll) calls a shared `Fail-Update` helper that reverts git, restores the three snapshots, restarts all 3 services (API → Collector → App, the same order the main script already stops/starts them in), and re-verifies health before giving up — previously EVERY one of those failures just did `Write-Warn` and kept going (this script was the most permissive of the three suite apps audited: it had literally zero fatal failure paths after pre-flight). A schema-migration failure still refuses to deploy the new code against a database it failed to migrate (schema.sql isn't applied in one transaction, so a code-level rollback can't undo a partial migration) but now also restores service instead of leaving the app down.
- Unlike DDIVault/LogVault, this script does NOT back up/restore `.env.local` for rollback — `Write-EnvFile` never regenerates it if it already exists, and `git clean` explicitly excludes it, so it's never mutated by a normal update run in the first place. Don't add an env-backup step here "for consistency with the other apps" — it would be dead code.
- Every run writes a BOM-free JSON result to `<InstallDir>\logs\last-update-status.json` (`[System.IO.File]::WriteAllText(..., UTF8Encoding($false))`, NOT `Out-File -Encoding UTF8` — the latter's BOM breaks Node's `JSON.parse` on the reading side, a bug caught and fixed in NetVault's own equivalent before it shipped here). `GET /api/system/last-update-status` (exempted from `enforceLicense`'s disabled block, same as its `/api/system/update-available` sibling — but deliberately NOT added to `middleware.ts`'s `PUBLIC_API` allowlist, since neither route needs to work with literally no session) surfaces it to `UpdateFailureBanner.tsx` (admin-only via `useRbac().canManageSettings`). **`<InstallDir>` is the `-InstallDir` PARAMETER, not `$AppRoot`** — on a normal suite install `$InstallDir` (e.g. `C:\Apps\SpanVault`) is the PARENT of `$AppRoot` (`C:\Apps\SpanVault\app`), so `logs\` is a SIBLING of the app folder, not inside it. The route shipped in 1.83.13 only checked `path.join(APP_ROOT, 'logs', ...)` and always returned `{exists:false}` as a result, even right after a real update — fixed in 1.83.15 to check both the sibling-of-APP_ROOT layout and the inside-APP_ROOT layout (a standalone install where `$InstallDir` and `$AppRoot` are the same directory), same dual-candidate-path pattern NetVault's equivalent route already used. If this route (or the PS1 script's own `$StatusPath`) is ever touched again, don't assume `logs\` lives inside `APP_ROOT` without checking both.
- `$ErrorActionPreference` is `'Continue'` for this whole script from right after pre-flight onward (already the case before this change) — every git/npm/nssm/psql call gates on `$LASTEXITCODE` explicitly rather than relying on PowerShell's own error-throwing. The new resilience code follows the same idiom; don't wrap it in `Stop`/relax-around-native-calls like NetVault/DDIVault do, that's a different (also valid) pattern this script doesn't use.
- (1.83.18) The ENTIRE main flow (STEP 1 through the success `Write-StatusJson`) is wrapped in a single top-level `try { ... } catch { Fail-Update -Stage $currentStage -Message "Unexpected error: ..." } finally { <remove lock file> }`. This closes a real gap: before this, rollback/status-write were ONLY reachable through the hardcoded `Fail-Update` calls at the five known failure sites — any OTHER exception (e.g. `(Get-Command X).Source` when `X` isn't found — note this actually returns an empty string rather than throwing in this PowerShell's default non-strict mode, so the genuinely dangerous case is a SILENT bad value, not a crash) killed the process with zero rollback and zero status file. `Fail-Update` itself still calls `exit 1` after rollback — that's fine, `finally` blocks still run during a script-scoped `exit` unwind (verified by hand), so the lock file always gets released. If you add a new stage, you don't need a new explicit `Fail-Update` call site for "unexpected" failures in it — the trap already covers it; only add an explicit call (with `$currentStage` set beforehand) when a SPECIFIC, anticipatable failure deserves a clearer message than the generic caught-exception one (see the `node` resolution check in STEP 7 for the pattern).
- (1.83.18) Concurrency guard: right after self-locating `$InstallDir` (before the transcript starts), the script checks `logs\update.lock` for a still-live recorded PID and exits immediately (no rollback, nothing touched) if one is found — otherwise it writes its own PID there and removes it in the top-level `finally` above. `POST /api/system/update` in `api/server.js` checks the SAME file (same dual-candidate suite/standalone path pattern as `last-update-status.json`) before scheduling the task and returns `409` if a run is already in progress, instead of unconditionally `schtasks /delete` + `/create` + `/run`. This exists because two overlapping runs previously could each stale-cleanup and re-snapshot the SAME `*.lastgood` directories, silently destroying one run's genuine rollback snapshot.
- (1.83.18) `Wait-Healthy` takes an optional `-ExpectedVersion` — when given, healthy also requires `/api/health`'s `version` field to match, not just `status -eq 'ok'`. The main flow's STEP 8 check passes `$attemptedVersion` (read from `package.json` right after the git reset in STEP 2); `Invoke-Rollback`'s own check passes `$prevVersion` (read from `package.json` in STEP 1.5, before git touches anything). Both are read via the new `Get-PackageVersion` helper, which returns `$null` (never throws) on anything missing/unparsable — a version-read failure silently degrades that run back to the old status-only check rather than blocking the update.
- (1.83.18) `Invoke-Rollback`'s three directory restores (`node_modules`/`.next`/`node_modules` again for frontend) now go through `Invoke-RestoreRename` (5 attempts, 2s apart) instead of a single `-ErrorAction Stop` `Rename-Item` — a transient post-service-stop file lock (the exact race this same function's neighboring comments already describe) used to turn into an immediate "ROLLBACK ALSO FAILED" with no retry at all.
- (1.83.18) `UpdatingOverlay` (settings page) no longer declares success purely from the health-poll transition. Once services are confirmed live it enters a `checking_result` phase that fetches `/api/system/last-update-status` (the same source `UpdateFailureBanner` reads) and branches three ways: clean success → `success` phase (green, auto-reloads to `/?updated=true`); `rolledBack: true` → `rolled_back` phase (amber, auto-reloads to `/?updateRolledBack=true` after the same settle countdown); rollback-also-failed → `rollback_failed` phase (red, **no auto-reload** — reloading a possibly-down app serves no one). Before navigating for the rolled-back/failed case, it also pre-seeds `UpdateFailureBanner`'s own sessionStorage dismiss key (`sv-update-failure-dismissed-<timestamp>`) for that SAME status-file timestamp, so the persistent banner doesn't immediately re-surface information the overlay just showed — it still fires normally for a genuinely later/different failed update. `(app)/page.tsx`'s `UpdatedNotice` now recognizes both `?updated=true` (green) and `?updateRolledBack=true` (amber) — never show the green copy for a rolled-back run.

## Schema / privilege
- `scripts/schema.sql` is idempotent and RE-APPLIED ON EVERY API STARTUP (since 1.25.2, via advisory lock) — not just at install time. It DOES contain an unconditional `GRANT SELECT ON ALL TABLES IN SCHEMA public TO nocvault_readonly`, and that's fine: the column-level exclusion (and, for `app_settings`, a row-filter view) lives directly in this same file, immediately AFTER that blanket grant — REVOKE-then-GRANT, since in Postgres the LAST statement touching a privilege wins. See `.ai-codex/schema.md`'s "Known schema debt"/"Privilege notes" for the full column lists.
- Never re-add a `host()`/`inet` cast on `netvault.devices.ip_address` when joining/importing — it's `character varying`, not `inet` (confirmed 2026-07 against live `information_schema.columns`; a cast here previously broke NetVault sync/import in three places).
- `wireless_controllers` holds 5 live secret columns (`api_key`, `api_password`, `api_client_secret`, `api_refresh_token`, `api_access_token`) — must always be column-level-excluded from any readonly diagnostic role, never table-wide granted.
- **Extended 2026-07-23 to three more tables + one settings key**, found by a full grep audit (the first pass only covered `wireless_controllers`): `monitored_devices` excludes `snmp_community`/`snmp_v3_auth_pass`/`snmp_v3_priv_pass` (widest blast radius — every monitored device, not just wireless gear; confirmed plaintext, no encryption anywhere in the collector), `agents` excludes `api_key` (the live WS bearer credential remote polling agents authenticate with), `agent_discovered_devices` excludes `snmp_community` (discovery-time working creds). `app_settings` is freeform key/value, so its `smtp_pass` value is excluded via a row-filtered `app_settings_public` VIEW instead of a column grant — both readonly roles' `SELECT` on the raw table is revoked. Same fail-closed rule applies to any new secret-shaped column/key added later: add it to the exclusion, don't assume it's automatically covered.

## Frontend conventions
- No sub-components defined inside another component's function body anywhere in the codebase currently (verified — see `.ai-codex/components.md`'s Violations section) — keep it that way; it causes input focus loss on every keystroke via remount-on-render.
- `api/` and `collector/` are plain JavaScript, zero TypeScript syntax (no `as string`, no type annotations) — only `frontend/src/` uses TypeScript.
- `frontend/next.config.js` has no `output: 'standalone'` — the NSSM service runs `next start -p 3008` directly; don't add standalone-build assumptions (static copying etc.) without checking this first.
- Design tokens (`--text-*`, `--bg-*`, `--tint-*`, `--surface-subtle`) are the suite-wide standard defined in `frontend/src/app/globals.css` — SpanVault is the REFERENCE implementation other NocVault apps copy from, not a follower. Hardcoded hex duplicating a token breaks dark mode. Sticky headers/toolbars must use an OPAQUE `var(--bg-card)`/`var(--bg-primary)`, never a semi-transparent tint — scrolled content bleeds through otherwise (worst in dark mode).
- **Wireless PDF reports had a site-scoping hole for five queries — the helper is now `wlCtrlClauses()`, never re-add a controller-only variant.** `api/reportsPdf.js` used to have `wlCtrlOnly(scope, col)` which applied the `controller_id` filter and SILENTLY DROPPED `scope.siteFilter`. All five call sites were affected (`wireless_intelligence` twice, `wireless_clients`, `wireless_ssids`, `wireless_controllers`), so a site_admin's wireless PDFs contained every site's data while the matching JSON endpoints — which DO scope, via `c.site_id` — correctly hid it. Measured on live data: 1253 clients returned instead of the caller's 372. Fixed by making the helper site-aware for every call site at once: `<col> IN (SELECT id FROM wireless_controllers WHERE site_id = ANY($n::int[]))`. This controller→site boundary is the same one already used for `wireless_rogue_aps`, and it is exactly as precise as `wlApClauses`' `a.site_id` filter because `wireless_aps.site_id` is itself copied from the owning controller by the collector. Do NOT "optimise" it into a join on `wireless_clients.ap_id` — `ap_id` is nullable (3 of 1262 live rows) so an AP join silently drops clients, whereas `controller_id` is `NOT NULL`.
- **`retry_rate_2g`/`retry_rate_5g` do not hold the same metric on every vendor.** Aruba writes a genuine retry percentage from the real OID (validated 0..100). **Cisco writes channel UTILIZATION** — `max(bsnAPIfLoadRxUtilization, .TxUtilization)` — because no true per-radio retry % is exposed there. Since `wireless_high_retry` alerts on this column against one threshold (`wireless_retry_threshold_pct`, default 15), the alert means a materially different thing per vendor and on Cisco will fire on ordinary busy-AP utilization. Left as-is deliberately (2026-08-04): separating them needs a schema change plus alert rework, and there is no Cisco hardware in this estate to validate a replacement against — that whole branch is UNVALIDATED. Re-check before onboarding the first Cisco WLC.
- **SNR→dBm conversions must use `>= 0`, not `> 0`.** Aruba/HPE report a positive SNR where a dBm is documented, converted with a typical -95 dBm noise floor (`sig - 95`). An SNR of exactly 0 is a REAL reading meaning "nothing above noise" (the weakest signal); with `> 0` it fell through to the raw branch and was stored as `0` dBm — the STRONGEST possible value, inverting the meaning. This was not theoretical: 6001 of 12361 live `wireless_rogue_aps` rows (49%) sat at exactly 0, so every "strongest rogue" ranking listed the faintest ones first. Fixed in `wireless/aruba.js` `parseRogueAps`; `clients/aruba.js` and `clients/hpe.js` already used `>= 0`. Rogue data self-heals within one poll (the upsert overwrites `rssi_dbm`, and rows are deleted after 24h) — no backfill needed.
- **MikroTik client→AP enrichment rests on an unvalidated index assumption**: it joins `mtxrWlRtabIface` to `mtxrWlApTable`'s index as though both number interfaces identically. No MikroTik device exists in this estate to confirm it. If the two tables are indexed independently, every client silently gets the WRONG ssid/band — wrong data, no error, nothing logged. Falsify on a RouterOS AP with 2+ wireless interfaces before trusting it.
- **AP↔controller ownership on an HA pair has no tie-break.** `upsertAp()` matches on `(site_id, name)` and points `controller_id` at whoever reported the AP most recently, which correctly collapses the HA duplicate — but if BOTH peers report the same AP in a cycle, `controller_id` ping-pongs every poll and anything grouped by controller (AP counts, licensed capacity, controller-scoped reports) flaps with it. There is no unique constraint on `(site_id, name)` anchoring it. Not occurring on this deployment (verified 2026-08-04: all 102 APs on controller 7, peer reports none). Detect with: `SELECT name, COUNT(DISTINCT controller_id) FROM wireless_aps GROUP BY name HAVING COUNT(DISTINCT controller_id) > 1;`
- **Device vendor/model/OS is a CROSS-DATABASE merge done in JS, not a SQL join — and it cannot become one.** `monitored_devices` has no model or OS column; that inventory lives in NetVault's `devices` table, a SEPARATE Postgres database, so `/api/devices` fetches it through the read-only `nv` pool (`netvaultInventory()`, 5-min cache) and merges by `netvault_device_id` first, then plain IP match. Three things to know before touching it: (1) it is deliberately best-effort — a NetVault outage must degrade Vendor/Model to "—", never fail the device list, so keep the `try/catch`; (2) `netvault.devices.ip_address` is `character varying`, NOT `inet`, so **no `host()` cast** (adding one throws `function host(character varying) does not exist` — the same cast has broken NetVault sync/import three times before); (3) coverage is partial by nature — on this install `netvault_device_id` is NULL for all 12 monitored devices, so every match is by IP and only 6 of 12 resolve. A device absent from NetVault correctly falls back to the SNMP-detected `device_vendor` and shows no model.
- **The devices list hides its "Version / OS" column when no device reports one.** NetVault's `os_type`/`os_version` are populated on 0 of 2,482 inventory rows here, so the column would otherwise be nothing but em-dashes on every row. `DevicesPage` computes `showOs` from the loaded devices and threads it down through `AgentGroup`/`SiteAccordion`/`DeviceRow` — the column reappears on its own as soon as any device has OS data. If you add a column with similarly sparse backing data, do the same rather than shipping a dead column.
- **A stretched (`flex:1`) link inside a click-to-toggle header steals most of the header's hit area.** `.sv-acc-head .site-nm` is an `<a>` to the site page and used to carry `flex:1`, so it stretched to fill the bar — measured live at 874px of a 1284px header (**68%**), meaning a click anywhere in the apparently-empty middle navigated to `/sites/:id` instead of expanding the section. It was invisible for as long as sites defaulted to OPEN (nobody clicked the header) and became a real trap the moment collapsed-by-default landed in 1.88.1 and expanding became the primary action. Fixed by giving the link `flex: 0 0 auto` and adding an explicit spacer `<span style={{flex:1}}/>` to absorb the width. General rule: inside a container whose own `onClick` is the main action, a nested link/button must hug its content — never let it flex — or it silently captures clicks meant for the container. Detect it by comparing the link's `getBoundingClientRect().width` against the header's, not by eye: both look identical rendered.
- **`navigator.clipboard` does NOT exist on this deployment — always provide the `execCommand` fallback.** The browser only exposes the async Clipboard API in a *secure context* (HTTPS or localhost). The suite is served over plain HTTP on a LAN IP, so `navigator.clipboard` is `undefined` — verified live 2026-08-06: `isSecureContext=false`, `navigator.clipboard=undefined`, `document.execCommand` present. A bare `navigator.clipboard.writeText(x)` THROWS a TypeError; the "safe-looking" `navigator.clipboard?.writeText(x)` is worse, because it silently does nothing while the UI closes as if the copy worked (that was the devices-page bug fixed in 1.88.3). Use the `copyText()` helper pattern in `app/(app)/devices/page.tsx` — try the real API only when `window.isSecureContext`, else a hidden `<textarea>` + `document.execCommand('copy')` — and surface the boolean result rather than assuming success. netvault's agents page and spanvault's maps page already do this correctly; several other call sites across the suite still do not.
- **`[FATAL] Cannot access 'wrap' before initialization` in SpanVault-API.err.log during a deploy is a TORN READ, not a code bug — check the timestamps before chasing it.** NSSM auto-restarts the managed process shortly after the updater kills it, so it can boot *while* `git reset --hard` is still rewriting `api/server.js`. Node then parses a file that is half old and half new, and the `wrap` helper is referenced above the line that declares it. Seen 8 times across the 2026-08-07 deploy; the service settled by itself and served HTTP 200 immediately afterwards. **How to tell it apart from a real TDZ error in 30 seconds:** a genuine one crash-loops forever, so (a) re-count the FATALs after 90s — a delta of 0 means it is historical, and (b) run the module-eval smoke test against the deployed file: `cd C:\Apps\SpanVault\app; node -e "require('./api/server.js')"`. `MODULE EVAL OK` followed by `EADDRINUSE` on 3009 is the PASS signal — it proves the module fully evaluated and reached its listen call, and only stopped because the live API already holds the port. `node --check` cannot detect a TDZ error at all, which is why this smoke test exists.
- **Unrelated, pre-existing, still open:** `[WS] Message error: could not determine data type of parameter $3` recurs in the same log — a real SQL parameter-typing fault in the agent WebSocket message handler (an untyped `$3` Postgres cannot infer). Not deploy-related and not caused by the 1.88.x work; needs an explicit cast at that call site.
- **`wireless_aps.mac_address` was NULL for every SNMP-discovered Aruba AP until 1.90.0 — the parser read the MAC and threw it away.** `collector/wireless/aruba.js`'s `parseApTable` iterates the `wlanAPTable` index, which IS the AP's MAC in dotted decimals (the same fact the "reject MAC-shaped names" guard right above it relies on), but never assigned it. Result: 213 of 224 APs had no MAC, so anything needing to resolve a MAC to an AP name had nothing to join against — which is why the Rogue APs table could only ever print the detecting AP's raw MAC. Fixed with `ap.mac_address = fmtMac(idx)`. After one poll cycle: 220 of 224 APs have a MAC and 12,578 of 12,578 rogue rows (100%) resolve to a name by EXACT match. If AP-name resolution ever regresses, check this assignment first.
- **Do not measure a resolution/coverage rate before the data it depends on has been repopulated — and do not reason from the reading you get.** Measuring the detecting-AP join immediately after deploying the parser fix gave 1.0% resolved, 0 exact matches, and everything coming from the first-five-octet fallback. That reading was real but unrepresentative: the only APs with a MAC at that moment came from the `aruba_central` API path, whose MACs genuinely differ from the SNMP radio MAC. It led to a code comment asserting "detecting_ap is a radio MAC offset from the base MAC, so both paths are needed" — which the post-poll measurement (100% exact, fallback never used) disproved. Wait for a collector cycle, re-measure, then write the explanation.
- **The Rogue APs table sorts and pages on the SERVER — do not "standardise" it onto `useTableSort` + `useClientPagination` like every other table.** There are 12.5k+ detections and only one 50-row page is ever in the browser, so client-side sorting would reorder those 50 and label the result "sorted by RSSI" — true of the page, false of the data. The API takes `sort`/`dir` against a **whitelist** (the value is interpolated into ORDER BY, so it must never come straight from the query string) plus `limit`/`offset`. `ORDER BY <col> <dir> NULLS LAST, r.id ASC` — the `r.id` tiebreak is load-bearing: without it, paging a column with many ties (rssi_dbm has hundreds at -95) lets equal rows shuffle between queries and you get duplicates on one page and gaps on the next. Verified zero overlap across adjacent pages on three different sort columns.
- **One expression, used by both the filter and the column it filters.** `ROGUE_BAND` and `DETECTING_AP_NAME` in `api/server.js` are each defined once and referenced by the SELECT, the WHERE and (for band) the filter. This is not tidiness: when display and search each resolved the detecting-AP name their own way, the column read "AP505-4" while search only matched the MAC, so searching the visible name returned nothing (fixed 1.90.3). Any new derived column that is also filterable should follow the same shape.

- ⛔ **`wireless_aps` channel has TWO writers — instrument both or you silently miss a whole vendor.** `wirelessCollector.js`'s `upsertAp()` writes it on every ~5-min poll, but `wireless/api/aruba-central.js`'s `pollRf()` also writes it directly on its own ~15-min cycle, and for aruba_central APs that is the ONLY writer (their main poll nulls channel by design, see `mapAp()`). Channel-change detection therefore lives in a shared `collector/wireless/channelChanges.js` called from BOTH; wiring only `upsertAp` looks complete and records nothing for every Central-managed AP. Same trap applies to any future "detect when field X changed" work on this table.
- `wireless_channel_changes.inferred_cause` is SUSPECTED, never confirmed. Polling sees the consequence of radar (an AP vacating a DFS channel 52-144 for a non-DFS one, which DFS mandates for 30 minutes), not radar itself. Real confirmation needs the controller's trap/syslog (Aruba `wlsxNRadarDetected`) — the Aruba controllers do NOT currently send syslog to LogVault (verified: 7 days of logs are 100% fortinet, zero 'radar'/'dfs' matches), so that ground truth does not exist in the suite yet. Don't relabel it as confirmed without that feed.

- ⛔ **Utilisation is NOT congestion — don't let a card measure one and claim the other.** `computeCongestionScore()` (collector/wirelessScore.js) weights util 35, retry 25, interference 15, band imbalance 15, weak clients 10; `high` is >= 60. So an AP at ~31% airtime can legitimately be HIGH, and a util-only filter will miss it. The Wireless Insights card used to filter `apUtil > 70` while its empty state said "No congestion detected", producing a green all-clear on the overview while the Access Points tab showed High for the same AP, same response, same render (fixed 1.93.2 — it now filters on `congestion_level === 'high' || apUtil > 70`). A false all-clear is worse than an absent card: it asserts the opposite of the truth instead of merely omitting it. Any new "problem APs" surface must filter on congestion_level, or say plainly that it is only showing airtime.

- The AP drawer's noise-floor smoothing window is SCALED to the selected range (`smoothingWindow()` in the wireless page), not fixed. The original window of 6 was tuned for 24h (~288 points); applied to a 1h view (~12 points) it averages away half the window and flattens exactly the detail the zoom was for. Below ~40 points smoothing is off entirely. If a new range is added, check the point count it produces against that function rather than assuming.

- ⛔ **Interface metrics are stored under the INDEXED name, not the canonical one.** `collector/discovery.js` builds each sensor with both a canonical `std_metric` (`if_in_bps`) and a per-interface `metric` (`if_2_in_bps`, ifIndex baked in) — and it is the INDEXED one that lands in `device_sensors.metric_name` and therefore `snmp_results`. Matching `metric_name = 'if_in_bps'` matches nothing for any normally-discovered device. `api/server.js` and `api/reportsPdf.js` always matched both; `api/intelligence.js` did not, so Capacity Forecasting showed "No bandwidth sensors configured — enable SNMP and run discovery" on 5 of 8 devices that had SNMP enabled, discovery run, and 15 days of bandwidth stored (fixed 1.94.1). The same equality test also silently built no bandwidth BASELINE, so bandwidth anomalies could never fire — a missing baseline reads as a calm network, which is why it went unnoticed. Match `LIKE '%in_bps'` / `'%out_bps'` (covers canonical, indexed, and the vendor parsers' `bandwidth_in_bps`). `snmp_results.if_index`/`if_name` are populated, so per-interface work is possible where it matters.

- ⛔ **The intelligence engine can only see `retention_raw_days` (default 14), no matter what interval a query asks for.** `collector.js`'s `retentionTick()` DELETEs from `ping_results`/`snmp_results` past that window every 12h. `detectPatterns()` used to query `INTERVAL '30 days'` and the Patterns tab told users patterns were "learned from 30+ days of history" — both were fiction, and neither produced an error, just a quietly halved analysis window. Two concrete consequences: (1) any per-day recurrence floor has to be judged against ~14 days, not 30; (2) a **day-of-week** pattern needs 7 days per occurrence, so a 3-occurrence floor requires 21+ days — at the default retention the weekly pass can never fire, which is why it is explicitly skipped (with a log line) rather than shipped as code that silently returns nothing. `patternLookbackDays()` now reads the setting so the window follows it. Before adding any new time-window analysis here, check the retention setting first — an `INTERVAL '90 days'` forecast over a 14-day table is not a slow feature, it is a wrong one.
- ⛔ **Confidence/quality scores must measure the claim, not the sample size.** `device_patterns.confidence` was `min(0.99, samples/30)`, and since every hourly bucket accrues hundreds of samples within days, all 58 stored patterns scored 0.96-0.99. The column rendered as a star rating that was identical on every row — it looked like a working feature and carried zero information. It now measures recurrence (elevated_days / observed_days). Same smell to watch for anywhere else a score is derived from row counts: if the value cannot come out low on real data, it is not a score.
- **A metric-detection engine that only writes never retires.** `detectPatterns()` upserts only the slots that still qualify, so a pattern that stops recurring is never revisited and sits in the UI at its last-known confidence indefinitely. Fixed with an age-out (`last_seen_at < NOW() - INTERVAL '3 days'`, against a 6h detection cycle). Any similar detect-and-upsert loop (thresholds, incidents) needs the matching purge, or the table only ever grows more stale.
- ⛔ **Never derive a displayed count from a page of rows.** The Anomalies tab's "N active" badge counted `status === 'active'` within the loaded 200 rows, so under the "All" filter it reported a fraction of the truth; separately the list itself capped at 200 of ~2,100 with no indication. Both are the same mistake as DDIVault's alert-count bug. The route now returns `X-Total-Count` and the UI issues a `limit=1` count-only companion request for the badge. If a list is capped, the cap must be visible on screen.
- ⛔ **A ratio has no sense of scale — relative-deviation detection needs an absolute floor or it manufactures findings.** `detectPatterns()` flagged a switch idling at 2.5% CPU that rose to 6% as "137% above normal, 13 of 14 days": it cleared the ratio bar, the recurrence bar and the confidence bar, and was still worthless. 24 of the 25 patterns found on this install were that shape (CPU 5-13%, latency 4-8ms). `PATTERN_FLOORS` in `api/intelligence.js` now also requires the elevated average to reach a level worth acting on (25% cpu/mem, 20ms latency; overridable via `pattern_min_cpu_pct` / `pattern_min_mem_pct` / `pattern_min_latency_ms` in `app_settings`), which leaves exactly 1. Anything else here that compares against a learned baseline — anomaly z-scores, threshold recommendations — should be checked for the same gap: on a quiet metric, "3 sigma" and "50% above normal" are both routinely reached by noise.
- ⛔ **A `try/catch` that degrades to an empty result turns a query bug into a false all-clear.** `/api/wireless/channel-changes/top` and the AP drawer's channel-change block both wrap their queries to survive an API deployed ahead of the schema step — but a blanket catch also swallows genuine errors, and an empty channel-change list renders as "no instability", asserting stability nobody measured. The first cut of the leaderboard query selected `a.controller_name` (it lives on `wireless_controllers`, not `wireless_aps`) and the catch would have made that a permanently empty green widget that no static check could catch. Both now degrade ONLY on `e.code === '42P01'` (undefined_table) and re-throw everything else. Rule: a fallback may only cover the specific condition it was written for — when the fallback's output is indistinguishable from good news, a broad catch is a correctness bug, not resilience. Same family as the congestion card's false all-clear (1.93.2).
- **`SectionCard` with `maxHeight` is an `overflowY:auto` scroll box — anything rendered after a long table is invisible.** The Channel Instability card's "tracking since 11 Aug" caveat was placed below its 10-row table inside a 280px card and could not be seen without scrolling, which is precisely backwards: the caveat is what stops a short list reading as a clean bill of health. Caveats, provenance notes and empty-state explanations go ABOVE the scrollable content in these cards, not after it. Check any new `maxHeight` card the same way — the build and type-check cannot see this, and a screenshot of the top of the card looks perfect.
